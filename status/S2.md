## 设计要点

- **谁来判**：接单程序判（退出码/stdout/stderr/进程状态/插件 classify）；中枢补它自己才知道的（不在线、没报到、规则没了、到上限）；Agent 在回执里自报 diagnosis 会信它；老回执中枢按结局补。
- **分组处理**：`need_owner`（need_login/need_approval/auth_invalid/env_missing）→ 不再自动重试，记 attempts 后转 cancelled，开提问卡片（选项「已恢复，重新派一轮」/「先不做了」，同 Agent 接续原会话）；`HOLD_MODEL`（rate_limited/quota_exhausted）→ 照常重试 + 写 `model_holds`（阶段 3 改派的接口，本阶段只写不消费）；其余自动类照上游节奏重试；unclassified 必须带原文+位置。
- **兼容**：diagnosis 可选、严格枚举；老设备交的回执中枢补分类，先升中枢后升设备。
- **通知**：`card.detail` 一行「设备 w1 · Agent a1（m1）· 分类：需要登录 · 下一步：需要本人处理」，放在各通道「来源」位置旁；兜底分类卡片正文带「原始输出：<目录>」。

## 原始输出说明

- 兜底/要人处理分类的 `diagnosis.output` 指向该轮目录 `worker/runs/<run>-<attempt>/`（entry.json + stdout/stderr/exit 文件），回执里同时带 `raw`（stderr 或 stdout 末尾 4K）。测试断言该目录真实存在（`existsSync`）。
- `receipt_unreadable` 卡片正文写「原文在 <out 文件>，留 14 天」，沿用上游 KEEP_DAYS。

## 第一轮全量测试的失败与修复

- `format.test.ts` 两处钉死字符串 `summary error usage"`：列名加了 diagnosis 后锚点失效 → 更新锚点。
- `worker.test.ts` 深比较整条结果：现在每轮都带 diagnosis → 断言拆成「老字段不变 + diagnosis.category=completed」。

## 已知不足

- `diagnose()` 的文字匹配只针对本阶段已写进 GENERIC 表的报错；认不出的统一 unclassified（带原文），不会误判成别的类。
- `model_holds` 只写不消费：阶段 3 改派逻辑还没接，`until` 到期的清理也没做（表会累积，量小）。
- need-owner 卡片固定两个选项，更细的「跳过这条规则」等动作留给后续。
- `receipt_unreadable` 的 next 按第一行结局给（failed→retry、其余→none），与实际重派行为一致，但 diagnosis.next 字段本身中枢不消费，只作展示。
