# 回执分类设计说明

对应实施方案 6.3 节、第 8 节阶段 2。本文是这一阶段的设计正本；与上游文档冲突处以 `docs/protocol.md` 现有行为为准。

## 1. 要解决的问题

上游回执（`Result`）只有结局（`done` / `nothing` / `failed` / `cancelled`）和一段自由文本。中枢拿到 `failed` 只能按固定节奏重试（5 分钟起、翻倍、上限 1 小时、第 3 次通知、第 10 次停），分不清是「该重试的临时故障」还是「白 retry 的要人处理」，人不在设备跟前也看不懂原因。

本阶段给回执加一个可选的结构化字段 `diagnosis`，让接单程序先说清「这是什么失败」，中枢按分组决定下一步。

## 2. 字段

`Result` 新增可选字段 `diagnosis`（放在结果层，不进回执代码块的 `ask/notice/…`）：

```jsonc
{
  "category": "rate_limited",          // 必填（有 diagnosis 时），分类代码见下
  "explain": "一句人能看懂的说明",       // ≤500 字
  "device": "office-mini",             // 接单程序名，≤200
  "agent": "claude-mini",              // rules.json 里的 Agent 编号，≤200
  "model": "claude-…",                 // Agent 配的模型，≤200
  "next": "wait_until",                // rerouted / wait_until / need_owner / retry / none
  "waitUntil": "2026-11-13T21:00:00+08:00", // ISO 带时区；解析不出就不带
  "raw": "原始报错原文（≤4000 字）",
  "output": "/设备上的输出目录或文件路径"      // ≤500，原始输出的位置
}
```

- `category`：有人填 `diagnosis` 时必填，只允许下表中的代码（严格枚举，见第 6 节兼容）。
- `next` 是说明性的：中枢按 `category` 分组决定实际行为，不信 `next` 的取值。
- `unclassified` 必须带 `raw` 和 `output`（原始输出位置），禁止只写「执行不了」。
- `raw` 是报错原文的尾部摘录（最多 4000 字）；`output` 是完整输出在这台设备上的路径，和「每轮输出留 14 天」配套。

## 3. 分类代码

按「中枢接下来怎么做」分六组（组名是文档用语，不进协议）：

| 组 | 分类代码 | 含义 | 谁判 | 中枢行为 |
| --- | --- | --- | --- | --- |
| 做成 | `completed` | 完成了 | 接单程序/中枢补 | 照常生效 |
| 做成 | `nothing_to_do` | 看过了没事可做 | 接单程序/中枢补 | 照常生效 |
| 自动处理 | `rate_limited` | 被限流 | 插件/通用规则 | 上游重试 + 记 `model_holds` |
| 自动处理 | `quota_exhausted` | 额度用尽 | 插件/通用规则 | 上游重试 + 记 `model_holds` |
| 自动处理 | `timeout` | 超过本轮时限被停 | 接单程序 | 上游重试 |
| 自动处理 | `stalled` | 已报完成但进程不退（卡住） | 接单程序 | 上游重试 |
| 自动处理 | `crashed` | 进程异常退出/消失 | 接单程序/通用规则 | 上游重试 |
| 自动处理 | `transient_error` | 临时网络或服务错误 | 通用规则 | 上游重试 |
| 自动处理 | `agent_error` | Agent 报错（已排除限流/额度） | 插件 | 上游重试 |
| 要人处理 | `need_login` | 需要登录/验证码/恢复连接 | 插件/通用规则 | 不重试 → 提问卡片 |
| 要人处理 | `need_approval` | 需要审批或拍板 | 插件 | 不重试 → 提问卡片 |
| 要人处理 | `auth_invalid` | 密钥过期、鉴权失效 | 插件/通用规则 | 不重试 → 提问卡片 |
| 要人处理 | `env_missing` | 目录不存在、CLI 没装、找不到命令/插件 | 接单程序/通用规则 | 不重试 → 提问卡片 |
| 中枢判断 | `worker_offline` | 接单程序不在线 | 中枢（sweep 离线卡片） | 现有卡片 + 分类标注 |
| 中枢判断 | `no_report` | 领走后 5 分钟没报到（情况不明） | 中枢（sweep unknown） | 现有卡片 + 分类标注 |
| 中枢判断 | `receipt_unreadable` | 回执读不懂、重写两次仍坏 | 接单程序（它有原文证据） | 按第一行结局生效，通知带分类 |
| 主动结束 | `owner_stopped` | 本人停止 | 中枢补 | 终态 |
| 主动结束 | `max_failures` | 连续 10 次没跑成 | 中枢 | 终态 + 通知带分类 |
| 主动结束 | `rule_deleted` | 规则删掉或改名 | 中枢 | 终态 + 通知带分类 |
| 兜底 | `unclassified` | 分不出来 | 接单程序兜底 | 上游重试；必须带 `raw` 和 `output` |

`receipt_unreadable` 在分组上属于「中枢判断」——回执作废后由中枢按第一行结局处理；但分类本身由接单程序写，因为只有它有原始输出和文件路径。其余「中枢判断」类由中枢在对应事件发生时自己标注（不进 `Result`）。

## 4. 谁来判、怎么判

### 接单程序（`worker/`）

一轮结束后（`conclude` 及各 `endWith` 出口），按以下顺序生成 `diagnosis`：

1. 结局是 `done` / `nothing` / `cancelled`：直接写 `completed` / `nothing_to_do` / `owner_stopped`。
2. `why === "timeout"` → `timeout`；`why === "finished"`（报了完成但 30 秒不退被停）→ `stalled`。
3. 回执重写后仍读不懂（`discardReceipt`）→ `receipt_unreadable`。
4. `failed`：先问插件的 `classify(stdout, stderr, code)`；插件没认出来再用 `worker/diagnose.ts` 的通用规则表匹配 stderr/stdout/错误文本；都认不出时：退出码 126/127 → `env_missing`，非零退出 → `crashed`，其他 → `unclassified`（必带 `raw` 和 `output`）。

通用规则表单独放在 `worker/diagnose.ts`：限流（429/rate limit…）、额度（quota/billing…）、鉴权失效（401/unauthorized/token expired…）、需要登录（not logged in…）、环境缺失（command not found/找不到目录/没有插件…）、临时错误（ECONN/5xx/网络…）。厂商特有的报错文本写在各插件自己的 `classify` 里，不进 `worker/`（纯净度测试不许内核/协议/接单程序提产品名）。已写进测试样例的格式都标「待真实样本校准」。

`waitUntil` 只在文本里能解析出明确等待时长时填（如 retry-after 秒数、Claude「resets at 时间」），解析不出就缺省——不猜。

### Agent 插件

`Adapter` 增加可选方法 `classify?(stdout, stderr, code): { category, explain?, waitUntil? } | null`。返回 `null` 表示插件没认出来，交给通用规则。本阶段实现三个内置插件：

- `command`：退出码 126/127 → `env_missing`；stderr/stdout 走通用规则；其余非零 → `crashed`。
- `claude`：从 stream-json 的最后一条 `result` 取报错文字（`is_error`、`subtype`、`errors`），加上自家格式规则（余额不足/超出用量 → `quota_exhausted`；登录/OAuth 失效 → `auth_invalid`、`need_login`；限流 → `rate_limited`），认得但没细分的 → `agent_error`。
- `codex`：从 `turn.failed`/`error` 事件的 `message` 取报错文字，加上自家格式规则，认得但没细分的 → `agent_error`。

### 中枢（`kernel/`）

- 结果带 `diagnosis`：原样存进 `runs.diagnosis`（JSON 串，随投影持久化），并按分组处理（见第 5 节）。
- 结果不带 `diagnosis`（老接单程序）：结局能确定的由中枢补上——`done`→`completed`、`nothing`→`nothing_to_do`、`cancelled`→`owner_stopped`；`failed` 没有证据不猜，留空，行为与旧版完全一致。
- 中枢自己产生的卡片（离线、情况不明、停止、达上限、规则没了）在卡片 `detail` 里标注对应分类。

## 5. 中枢按分组处理

`kernel/decide.ts` 的 `finish`：

- `done` / `nothing` / `cancelled`：照旧 `applyReceipt`/停止分支，只是把 `diagnosis` 存下。
- `failed` + 要人处理类（`need_login`/`need_approval`/`auth_invalid`/`env_missing`）：**不走 `retryLater`**。这一轮记 `attempts+1` 后记为 `cancelled`（保留 error、session、usage、去重标记），并开一张 `ask` 提问卡片：
  - `key` = `run:<id>:need-owner`，`kind` = `ask`，带 `detail`（见第 7 节）。
  - 选项：「已恢复，重新派一轮」（推荐）/「先不做了」。本人答了沿用上游回答机制：产生 `card.answered` 事件、回到同事项排队新一轮、同 Agent 时接续原会话。`about` 写清：恢复了就只做剩余步骤；选了不做就回没事可做。
  - 失败回执只能发通知的限制不变（`ask`/`resolve`/`later`/`events` 照旧进 `rejected`）。
- `failed` + `rate_limited`/`quota_exhausted`：照常 `retryLater`；另外把模型记进新的 `model_holds` 投影表：`{ model, until, reason, by:"receipt", run, at }`。`until` 用 `diagnosis.waitUntil`，没有就是 `null`（未知，阶段 3 决定含义）。**本阶段不改派**；`model_holds` 就是留给阶段 3 派单逻辑的接口，`/v1/state` 的 `modelHolds` 顺带把它带出来。
- `failed` + 其他（自动处理、兜底、未分类）：照旧 `retryLater`。
- `cancelled`（含停止中交 `failed`）：中枢补 `owner_stopped`。
- 连续第 10 次（`MAX_ATTEMPTS`）、规则没了、本人停止：通知卡片 `detail` 标注 `max_failures` / `rule_deleted` / `owner_stopped`。
- `sweep` 的离线卡片、情况不明卡片：`detail` 标注 `worker_offline` / `no_report`。

## 6. 兼容与升级顺序

- `diagnosis` 是可选字段：老回执一切照旧；新中枢收到老接单程序的回执按第 4 节补能确定的分类。
- `category` 用严格枚举校验：不认识的分类直接 400 拒收。升级顺序必须是**先中枢、后设备**——新分类先入中枢发版，设备再跟上，中间不会出现设备发来中枢不认识的分类（和实施顺序一致）。
- `next`/`explain`/`raw`/`output` 等都是说明性字段，不影响事务正确性；中枢只按 `category` 分组行动。
- 卡片 `detail` 也是可选字段：老通道不认识就当没有，所有通道先看 `text` 正文也带同样的信息。

## 7. 通知

在上游「来源：<规则>」的位置追加一行 `detail`：`设备 <名> · Agent <编号>（模型 <名>）· 分类：<代码> · 下一步：<话>`。

- `detail` 存在卡片行上（可空），`cardView` 带出；飞书（正文首行）、桌面通知、Webhook 正文、卡片网页 `.from` 段、`agent-autoloop status` 卡片段都在来源行旁显示。
- 卡片正文同时带「一句说明」（`explain`）和「下一步」；`unclassified` 的通知必须带 `output` 里的原始输出位置。
- 提问卡片的 `text` = 说明 + 分类明细 + 下一步；选项如上。

## 8. 与上游重试的关系

- 上游 `retryLater` 语义不变：指数退避、同事项新事件并入、第 3 次通知、第 10 次停止。本阶段只是在它前面加一个分流：要人处理类不再进重试队列，直接转终态 + 提问卡片。
- 改派（rate_limited/quota_exhausted → 换 Agent/模型）属于阶段 3；本阶段只写 `model_holds` 记录事实，不在派单逻辑里消费。
- 「一轮不等人」原则保持：要人处理不阻塞、不占进程，靠卡片回答唤醒新一轮。

## 9. 已知不足 / 待校准

- 各厂商报错文本按已知公开格式写规则；真实样本碰到后补进 `worker/diagnose.ts` 或对应插件并校准测试（详见 status/S2.md 清单）。
- `waitUntil` 只解析相对时长和明确的重置时刻；解析不出记 `null`，阶段 3 按模型周期兜底。
- `need_approval` 暂无真实触发路径（内置插件后台跑批不会碰到审批），保留分类供后续插件使用。
- `stalled` 只覆盖「报了完成不退场」这一种卡住；运行中无输出的心跳级卡住仍走 `no_report`/超时。
